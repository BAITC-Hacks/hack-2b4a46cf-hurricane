# Чеклист подготовки по критериям оценивания

Всего 100 баллов. Ограничение по времени — 5 часов разработки на площадке.
Что можно сделать до старта — помечено **[до]**, что только во время хакатона — **[на месте]**.

---

## 1. Соответствие кейсу и функциональность — 20

Проверяют: обязательные требования кейса выполнены, основной сценарий работает от входа до результата. Считают только то, что реально работает.

- [ ] **[на месте]** Прочитать кейс дважды. Выписать обязательные требования отдельным списком в README (раздел «Требования кейса → статус»).
- [ ] **[на месте]** Определить один основной сценарий (happy path) и зафиксировать его словами: вход → шаги → выход.
- [ ] **[на месте]** Сначала довести happy path до конца сквозь все слои, потом улучшать. Никаких «почти работает».
- [ ] **[на месте]** Каждые ~60 минут прогонять основной сценарий руками и чинить, если сломался.
- [ ] **[на месте]** Не начинать фичи, которые не влезут в оставшееся время. Недоделанное — под флаг или в ветку, в main только рабочее.
- [ ] **[до]** Подготовить локально шаблоны: заглушка UI/CLI, каркас API, подключение к LLM, чтение конфигов. На месте это экономит первый час.

## 2. Техническая реализация — 25

Проверяют: заявленное реально реализовано в коде, компоненты связаны, структура понятна, нет хардкода ответов и имитации. Учитывают лимит 5 часов.

- [ ] **[на месте]** Никаких захардкоженных «правильных ответов» и моков в основном пути. Если что-то заглушено — честно написать в README в разделе «Ограничения».
- [ ] **[на месте]** Понятная структура: `src/` или аналог, разделение на слои (api / core / storage / ui), названия по смыслу.
- [ ] **[на месте]** README не обещает больше, чем есть в коде. Каждая фича из README должна находиться в коде за минуту.
- [ ] **[на месте]** Коммиты небольшие, с осмысленными сообщениями, история отражает 5 часов работы. Первый коммит — после официального старта.
- [ ] **[до]** Договориться в команде о стеке, линтере, форматтере, структуре папок. Не спорить об этом на месте.
- [ ] **[до]** Подготовить локальный шаблон проекта (без пуша в репо Организатора).

## 3. README и техническая документация — 20

Проверяют: README заменяет презентацию. Из него понятно, что сделано, как устроено, какие технологии и данные, как установить и запустить, как проверить основной сценарий, какие ограничения. Оценивается содержание, не оформление.

- [ ] **[до]** Заготовить шаблон README с разделами:
  1. Что это и какую задачу решает (2–3 предложения)
  2. Что реализовано (список фич со статусом)
  3. Архитектура (схема или список компонентов и как они связаны)
  4. Технологии и данные (стек, модели, датасеты, внешние API)
  5. Установка и запуск (пошагово, с командами)
  6. Как проверить основной сценарий (конкретные шаги, ожидаемый результат)
  7. Переменные окружения (таблица: имя, назначение, пример)
  8. Известные ограничения и что не успели
  9. Команда
- [ ] **[на месте]** Заполнять README параллельно с кодом, а не в последние 15 минут. Назначить ответственного.
- [ ] **[на месте]** Раздел «Как проверить» писать так, чтобы эксперт мог повторить за 5 минут без вопросов.
- [ ] **[на месте]** Честный раздел «Ограничения». Это плюс, а не минус: показывает, что команда понимает своё решение.
- [ ] **[на месте]** За 20 минут до сдачи: прочитать README глазами человека, который видит проект впервые.

## 4. Воспроизводимость и готовность к развёртыванию — 20

Проверяют: жюри может запустить проект в чистом окружении. Зависимости, конфигурация, env, данные подготовлены. Деплой — плюс, но не заменяет запуск из репо.

- [ ] **[до]** Подготовить локально `Dockerfile` и `docker-compose.yml` для типового стека.
- [ ] **[до]** Подготовить `.env.example` со всеми переменными и комментариями. Реальный `.env` — в `.gitignore`.
- [ ] **[до]** Проверить, что на ноутбуке работает Podman/Docker, есть образы базовых зависимостей (python, node, postgres и т.д.), чтобы не качать на площадке.
- [ ] **[на месте]** Зафиксировать версии зависимостей (lock-файл: `package-lock.json`, `uv.lock`, `poetry.lock`, `requirements.txt` с версиями).
- [ ] **[на месте]** Одна команда для запуска: `docker compose up` или `make run`. Максимум две-три.
- [ ] **[на месте]** Если нужны данные (сиды, датасет, модель) — положить в репо или скрипт, который их скачивает. Указать источник и размер.
- [ ] **[на месте]** Не полагаться на локальные пути, установленные глобально пакеты, кэш.
- [ ] **[на месте]** За 40 минут до сдачи: склонировать репо в чистую папку и запустить по README с нуля. Всё, что сломалось, — чинить приоритетно.
- [ ] **[на месте]** Если есть время — задеплоить (Railway, Render, Vercel, VPS) и дать ссылку в README. Это бонус, не обязаловка.

## 5. Базовая надёжность и безопасность — 15

Проверяют: основной сценарий не падает на корректных данных, очевидные некорректные запросы обрабатываются.

- [ ] **[на месте]** Валидация входа на границе: пустые поля, неверный тип, слишком большой размер, неподдерживаемый формат файла.
- [ ] **[на месте]** Понятные ошибки вместо стектрейса: 400 с сообщением, а не 500.
- [ ] **[на месте]** Обработка падений внешних сервисов (LLM API, БД): таймаут, retry или понятное сообщение пользователю.
- [ ] **[на месте]** Секреты только через env. Проверить `git log -p | grep -i key` перед сдачей: ни одного ключа в истории.
- [ ] **[на месте]** Нет SQL-конкатенации, нет `eval`, нет выполнения пользовательского ввода как кода.
- [ ] **[на месте]** Health-check эндпоинт или простая команда проверки, что сервис жив.
- [ ] **[на месте]** Прогнать 5–7 «глупых» запросов руками: пустой, огромный, с мусором, с юникодом, повторный. Ничего не должно падать.

## Тайминг на 5 часов (ориентир)

| Время | Что делаем | Критерии |
|---|---|---|
| 0:00–0:20 | Разбор кейса, выбор сценария, распределение ролей, первый коммит скелета | 1, 2 |
| 0:20–2:30 | Happy path сквозь все слои | 1, 2 |
| 2:30–3:30 | Валидация, обработка ошибок, доводка | 5, 1 |
| 3:30–4:15 | Docker, env, lock-файлы, README | 4, 3 |
| 4:15–4:40 | Чистый клон и запуск по README, фикс поломок | 4, 3 |
| 4:40–5:00 | Финальная вычитка README, проверка секретов, последний коммит | 3, 5 |

## Что подготовить до старта (не пушить в репо Организатора)

- Шаблон проекта под согласованный стек
- Шаблон README
- Dockerfile + compose + `.env.example`
- Скачанные базовые образы и зависимости
- Аккаунты и ключи к LLM API, проверенные лимиты
- Переходник LAN, зарядка, запасной интернет
