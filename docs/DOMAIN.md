# Предметная область

Рабочий документ команды. Заполнен по [docs/hackathon/TASK.md](hackathon/TASK.md). Разделы «Сущности» и «API» заморожены: изменения только через Alembic‑миграцию плюс `yarn api:types`, и о них говорят вслух всей команде.

## 1. Проблема

> Заказчик мероприятия вводит город, дату, тип события, категорию подрядчика и бюджет и получает до трёх карточек свободных подрядчиков с конкретным объяснением, почему каждый подходит, чтобы выбрать из каталога за минуту, а не перечитывать 15 профилей.

Аналоги:

- Маркетплейсы услуг (Profi, YouDo): паттерн «фильтры → список карточек». Берём карточку с ценой и городом. Отличаемся тем, что показываем не список, а три карточки с объяснением и явно говорим, почему остальные не прошли.
- Подборки «почему мы вам это рекомендуем» у Booking: одна строка причины под карточкой. Берём формат «факт про заказ → факт про подрядчика».

## 2. Основной сценарий

1. Пользователь открывает главную и заполняет форму: город, дата, тип мероприятия, категория, бюджет. Опционально длительность и язык. Списки значений приходят с бэкенда из каталога, не хардкодятся.
2. Система жёстко фильтрует каталог: город совпадает, категория входит в `categories`, дата не в `busy_dates`, тип входит в `event_formats`, `price_from_kzt` не выше бюджета, при указании длительности `max_hours` пустой или не меньше её, при указании языка он есть в `languages`. Каждый отсев считается по причине.
3. Система ранжирует прошедших детерминированно: запас по бюджету, совпадение языка, запас по часам, упоминание формата мероприятия в описании. Эмбеддинги отложены до второй версии. Настоящие профили при равном счёте выше синтетических. Финальный тай‑брейк по `id`.
4. Система берёт до трёх лучших и одним вызовом LLM получает для каждого 1–2 предложения объяснения. В промпт уходят только вычисленные факты (сколько сэкономлено от бюджета, какой формат совпал, что свободен на дату, цитата из описания), LLM их пересказывает, а не придумывает. Общие фразы запрещены промптом, порядок карточек LLM не меняет.
5. Пользователь видит один из трёх исходов: карточки с объяснениями; «в городе нет такой категории»; «кандидаты есть (N), но никто не прошёл: занято на дату 4, дороже бюджета 2, не берут формат 1». Если карточек меньше трёх, под ними та же расшифровка причин.
6. Каждый запрос и ответ пишется в `runs` для истории и проверки детерминизма.

Некорректный ввод, который сценарий обязан переживать: дата вне окна 23.09.2026 – 31.12.2026 → 400 с текстом про окно каталога; бюджет ≤ 0 или нечисло → 422; неизвестный город или категория → исход «нет такой категории», не ошибка; OpenAI недоступен → карточки всё равно отдаются с объяснением из шаблона по тем же фактам и флагом `explanation_source: "template"`; пробелы и регистр во входе не важны.

## 3. Сущности

| Сущность | Поля (тип) | Связи | Из какого шага |
|---|---|---|---|
| `vendors` | `id str` (`HK-…`), `name str`, `categories list[str]`, `city str`, `price_from_kzt int`, `event_formats list[str]`, `languages list[str]`, `max_hours int \| null`, `busy_dates list[date]`, `description text`, `synthetic bool`, `city_imputed bool`, `price_imputed bool`, `created_at` | | шаги 2–4, загрузка `python -m src.seed` из `app/data/vendors.csv`, upsert по `id` |
| `runs` | `id`, `prompt text`, `response jsonb`, `model str`, `duration_ms int`, `created_at` | | шаг 6 |

Списки хранятся как `ARRAY(String)` / `ARRAY(Date)`, каталог маленький, join‑таблицы и индексы кроме PK не нужны. Seed идемпотентный: запускается после миграций в compose (сервис `seed`) и в `preDeployCommand` на Railway.

Текстовая ERD:

```
runs               (история запросов и ответов)
vendors            (независимый каталог, читается фильтром)
```

## 4. API

| Шаг | Метод и путь | Вход (схема) | Выход (схема) | Ошибки |
|---|---|---|---|---|
| 1 | `GET /catalog/options` | | `CatalogOptionsOut` (`cities`, `categories`, `event_formats`, `languages`, `date_from`, `date_to`) | 500 |
| 2–5 | `POST /recommend` | `RecommendIn` (`city`, `event_date`, `event_format`, `category`, `budget_kzt`, `duration_hours?`, `language?`) | `RecommendOut` (`outcome: Literal["matched","no_category_in_city","no_candidates_pass"]`, `cards: list[VendorCardOut]`, `rejected: RejectedOut` со счётчиками по причинам, `explanation_source: Literal["llm","template"]`) | 400, 422, 502 |

`VendorCardOut`: `id`, `name`, `category`, `city`, `price_from_kzt`, `explanation`, `synthetic`, `matched_on: list[str]` (какие условия совпали, для бэджей на карточке).

Детерминизм: ранжирование без LLM, `temperature=0` и `seed` в вызове объяснений. Один вызов LLM на все три карточки с таймаутом 8 с, без ретраев: при таймауте сразу шаблонные объяснения, чтобы ответ пришёл в ориентир 10 с.

Паттерн: **форма → результат**.

Экран 1 (`ui/src/routes/index.tsx`): форма из 5 обязательных полей и раскрывающегося блока «Длительность, язык». Одна главная кнопка «Подобрать». Дёргает `GET /catalog/options` при загрузке, `POST /recommend` по кнопке. Ниже результат в одном из состояний: загрузка с текстом «Подбираю…», три исхода из шага 5, ошибка с подсказкой что делать. ## 6. Деление работы

| Кто | Слой | Первый коммит |
|---|---|---|
| | бэкенд: `vendors` в `models.py`, миграция, загрузка CSV, `recommend.py` с фильтром и ранжированием | миграция, сид каталога, `POST /recommend` без объяснений, `yarn api:types` |
| | фронт: форма и карточки против `api-types.ts`, четыре состояния | экран на реальном эндпоинте |
| | LLM: промпт объяснений в `llm.py`, шаблонный фолбэк; потом README, деплой, три демо‑запроса | `llm.py` с реальным вызовом и запретом общих фраз |

## 7. Вне области

- Бронирование, заявки, уведомления подрядчику.
- Свои синтетические профили: добавляем только если для демо редкой категории не хватит данных, с `synthetic: true`.
- Авторизация: все эндпоинты открыты, учётных записей нет.
- Дообучение моделей, pgvector, кеш результатов, пагинация.
- Фильтр «Зарубежье» как отдельный сценарий: город в списке есть, обрабатывается общим правилом.
