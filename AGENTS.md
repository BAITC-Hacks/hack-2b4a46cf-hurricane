# Правила проекта

Монорепо: `app/` бэкенд (FastAPI), `ui/` фронтенд (React). Цель: рабочий основной сценарий от входа до результата, код читается за минуту незнакомым человеком.

## Стек, не обсуждается
- Бэкенд: Python 3.12, uv, FastAPI, SQLAlchemy 2 (async), Alembic, Pydantic v2, asyncpg, `openai` SDK. `taskiq` только если появятся отложенные задачи или расписание.
- Фронтенд: React 19, TypeScript, Vite 7, yarn 1, Lingui 5, Tailwind CSS v4, shadcn поверх Base UI (`@base-ui/react`). Компоненты добавляются командой `npx shadcn@latest add <name>`, живут в `ui/src/components/ui/`, правятся руками как свой код.
- Инфра: Postgres 17, `docker-compose.yml`, деплой бэкенда и фронтенда на Railway (два сервиса из монорепо плюс плагин Postgres).

## Кросс-платформенность (macOS + Windows в одной команде)
- Никаких shell-скриптов, `Makefile`, `bash -c` в проекте. Команды только `docker compose ...`, `uv run ...`, `yarn ...`. Единственная точка входа для локального запуска: `python dev.py` (stdlib, без зависимостей). Новые шаги настройки добавляются в него, а не в README-инструкции.
- Пути в коде через `pathlib` / `path.join`, никаких строк с `/` или `\`.
- Конфиг только из `.env` через pydantic-settings и Vite. Никаких `export VAR=` в инструкциях.
- Перевод строки LF везде (`.gitattributes` уже настроен). Не менять.
- Данные Postgres только в named volume, не в bind mount.
- Host-порты compose задаются через `APP_PORT`, `UI_PORT`, `DB_PORT` в `.env`, если стандартные заняты. Внутри контейнеров порты не меняются.

## Имена: паттерн A/HC/LC
Имя функции = `prefix? + action + highContext + lowContext?`. Читается как предложение.

| Часть | Что это | Примеры |
|---|---|---|
| action | глагол: `get`, `set`, `fetch`, `create`, `remove`, `handle`, `should`, `is`, `has` | `get`, `handle` |
| high context | над чем | `User`, `Invoice` |
| low context | уточнение, если нужно | `Messages`, `Outside` |

- `getUser`, `getUserMessages`, `handleClickOutside`, `shouldShowModal`, `isLoading`, `hasAccess`.
- Python то же самое в snake_case: `get_user_messages`, `should_send_reminder`, `is_valid_hash`.
- Без сокращений: `user`, не `usr`; `message`, не `msg`. Без `data`, `info`, `item`, `temp`, `result` как самостоятельных имён.
- Не дублировать контекст: внутри `MenuItem` метод `handleClick`, а не `handleMenuItemClick`.
- Имя отражает результат: `isDisabled`, а не `isEnabled` с `!` при вызове.
- `fetch` для сетевых запросов, `get` для синхронного доступа к тому, что уже есть.

## Минимализм
- Файл до ~200 строк. Перевалил — дели по смыслу, а не на `utils`.
- Функция помещается на экран (~30 строк). Вложенность не глубже двух уровней, дальше early return.
- Никаких абстракций впрок: нет базовых классов, интерфейсов и фабрик с одной реализацией, нет DI-контейнеров, generic-репозиториев, event bus. Абстракция появляется на третьем повторе.
- Библиотека и stdlib всегда лучше своего кода. Не писать retry, парсеры дат, http-клиенты.
- Нет папок `utils/`, `helpers/`, `common/`. Функция живёт рядом с тем, кто её вызывает.
- Комментарий отвечает только на «почему». Комментариев «что делает код» нет. Одна строка docstring на модуль.
- Мёртвый код удаляется сразу: закомментированные блоки, неиспользуемые импорты, `TODO` без владельца.

## Тесты
Тесты не обязательны и не блокируют фичи. Если пишутся, то только на основной сценарий API: pytest в `app/tests/`, без e2e, UI-тестов и тестов ради покрытия. Основная проверка руками по разделу README «Как проверить».

## Структура бэкенда `app/src/`
- `main.py` FastAPI-приложение, роутеры, CORS, `/health`.
- `config.py` настройки из env, читаются один раз.
- `db.py` engine, session, `Base`, зависимость `get_session`.
- `models.py` таблицы. `schemas.py` pydantic-схемы входа/выхода.
- `errors.py` один `AppError` и его обработчик. Ошибки ввода → 400, внешний сервис → 502.
- `llm.py` вызовы OpenAI.
- Новые фичи: один модуль с роутером, например `invoices.py`, подключается в `main.py`. У каждого эндпоинта `response_model` из `schemas.py`: без него фронт не получит тип ответа.
- Схема БД меняется только через Alembic, файлы в `app/migrations/`: `uv run alembic revision --autogenerate -m "add invoices"`. Контейнер `migrate` применяет миграции сам при `docker compose up`.

## Структура фронтенда `ui/src/`
- `main.tsx` точка входа: i18n, `QueryClientProvider`, `RouterProvider`. `api.ts` все запросы к бэкенду через типизированный `openapi-fetch`. `i18n.ts` локали.
- `api-types.ts` генерируется из `/openapi.json` командой `yarn api:types` при запущенном бэкенде. Руками не правится, коммитится. Типы запросов и ответов берутся только из него: `components["schemas"]["AskOut"]`, свои дубликаты типов API не пишутся.
- Роутинг: TanStack Router, file-based. Экран = файл в `routes/`: `routes/index.tsx` это `/`, `routes/users.tsx` это `/users`, `routes/__root.tsx` общий каркас с шапкой. `routeTree.gen.ts` генерируется Vite-плагином при `yarn dev` и `yarn build`, руками не правится, коммитится.
- Данные: TanStack Query. Чтение через `useQuery({ queryKey, queryFn })`, запись через `useMutation`. Функции `queryFn` живут в `api.ts`. Никаких `useEffect` + `fetch` + `useState` для загрузки данных.
- Таблицы: TanStack Table (`@tanstack/react-table`) поверх shadcn `Table`. Общий компонент таблицы появится вместе с первым списком данных.
- Свой компонент = один файл в `components/`. Примитивы shadcn в `components/ui/`.
- Импорты через алиас `@/`: `import { Button } from "@/components/ui/button"`.
- Стили только Tailwind-классами. Свой CSS не пишется, `index.css` содержит только импорты и токены темы shadcn.
- Вёрстка адаптивная, desktop first: базовые классы под десктоп, мобильные переопределения через `max-md:` (`max-md:flex-col`, `max-md:w-full`). Не использовать `md:`/`lg:` (это mobile first).
- Иконки только из `lucide-react`.
- Визуальный стиль по [DESIGN.md](DESIGN.md) (дизайн-система на основе Vercel). Цвета, радиусы, отступы и шрифты берутся оттуда через токены shadcn в `index.css`, не хардкодятся в классах.

## UX: законы, которым подчиняется каждый экран
Источник: [Laws of UX](https://lawsofux.com/). Перед тем как считать экран готовым, агент проверяет его по этому списку.

- **Jakob's Law.** Привычные паттерны, никаких изобретённых контролов. Форма выглядит как форма, кнопка как кнопка. Компоненты shadcn использовать как есть.
- **Hick's Law.** На экране одно главное действие и не больше 5 вариантов выбора. Второстепенное скрыто за раскрытием, а не выложено сразу.
- **Fitts's Law.** Кликабельные цели не меньше 40px по высоте, на мобильном 44px. Главная кнопка рядом с полем, к которому относится. На мобильном кнопки во всю ширину.
- **Miller's Law.** Длинные списки и формы разбиты на группы по 5–7 элементов. Группа = `Card` или секция с заголовком.
- **Law of Proximity / Common Region.** Связанные поля стоят рядом и внутри одной рамки. Подпись прямо над полем, ошибка прямо под ним.
- **Doherty Threshold.** Отклик на действие быстрее 400 мс. Кнопка сразу переходит в состояние загрузки и блокируется, для запросов к LLM показывается индикатор с текстом («Думаю…»). Пустое ожидание без индикатора запрещено.
- **Von Restorff Effect.** Один акцентный элемент на экран: главная кнопка. Всё остальное нейтральное. Два одинаково ярких действия рядом запрещены.
- **Postel's Law.** Вход принимается мягко: пробелы обрезаются, регистр не важен, вставка из буфера работает. Вывод строгий и предсказуемый.
- **Tesler's Law.** Сложность живёт в бэкенде. Поля с разумными значениями по умолчанию, пользователь не выбирает то, что можно угадать.
- **Peak-End Rule.** Экран результата самый вылизанный: чёткий заголовок, читаемый вывод, следующее действие. Ошибка говорит, что делать дальше, а не показывает код.
- **Goal-Gradient / Zeigarnik.** Многошаговый сценарий показывает, где пользователь находится и сколько осталось.
- **Aesthetic-Usability Effect.** Единая сетка отступов и типографика по DESIGN.md. Выравнивание важнее украшений.
- **Cognitive Load.** Одна задача на экран. Нет вводных текстов и инструкций: если интерфейсу нужна инструкция, интерфейс переделывается.
- **Состояния.** У каждого экрана есть четыре состояния: загрузка, пусто, ошибка, данные. Все четыре реализованы, а не только «данные».
- Все строки интерфейса через Lingui-макросы `t` и `<Trans>`. Хардкод текста запрещён. После добавления строк: `yarn lingui:extract`.

## Асинхронность (бэкенд)
- Весь ввод-вывод в бэкенде асинхронный. Роутеры и зависимости объявляются `async def`.
- OpenAI и NVIDIA только через `AsyncOpenAI` с `await`. Синхронный `OpenAI()` не используется.
- HTTP-запросы к сторонним API только через `httpx.AsyncClient`. Никаких `requests`.
- БД только через async-сессию из `db.py`. Никаких `psycopg2`, `create_engine` и синхронных сессий.
- Блокирующий код (CPU-тяжёлая обработка, синхронная библиотека без async-версии) оборачивается в `asyncio.to_thread(...)`. Если работа длиннее пары секунд, она уходит в `taskiq`, а не держит запрос.
- Несколько независимых внешних вызовов запускаются параллельно через `asyncio.gather`, а не последовательно.

## Ошибки и надёжность
- Вход валидируется один раз на границе (Pydantic). Внутри ходят простые типы.
- Внешние вызовы (OpenAI, БД) с таймаутом. Никаких пустых `except`.
- Секреты только через env. Ни одного ключа в коде, логах, README, коммитах.
- Никаких моков и захардкоженных ответов в основном пути. Если что-то заглушено, пометить `# STUB:` и записать в README «Ограничения».

## Docker
Минимальный `slim`/`alpine` образ с фиксированной версией, `.dockerignore`, манифесты копируются раньше кода, один `RUN` с очисткой кэша, `COPY` а не `ADD`, multi-stage, non-root пользователь, секреты только через `--mount=type=secret` или env в рантайме, exec-форма `CMD` для graceful shutdown, `HEALTHCHECK`. Проверка: `docker run --rm -i hadolint/hadolint < app/Dockerfile`.

## Git
- **Обязательно:** в сообщениях коммитов нет упоминаний соавторства с Claude, Codex или любым ИИ. Нет `Co-Authored-By`, нет «Generated with». Хук `.githooks/commit-msg` это проверяет, включить: `git config core.hooksPath .githooks`.
- Коммит на одну законченную вещь, сообщение в императиве: `add invoice parser`.
- В `main` только работающее. Недоделанное в ветку.

## Деплой
- Полная инструкция: [DEPLOYMENT.md](DEPLOYMENT.md). Читать перед первым деплоем.
- **Обязательно у каждого:** Railway CLI установлен и залогинен (`railway whoami`), Railway MCP подключён в project scope: `.mcp.json` (Claude Code) и `.codex/config.toml` (Codex CLI). Конфиги в репо, менять не нужно.
- Окружение Railway одно: `production` в проекте `hurricane`. Автодеплоя из GitHub нет (репозиторий Организатора, Railway GitHub App туда не ставится), деплой только руками: скилл `/deploy` или `railway up` из `app/`.
- В `production` катить проверенное локально, окружение общее на команду. Переменные и сервисы не удалять, ломающие изменения согласовывать.
- Фронт: сервис `ui` на Railway собирается из последнего stage `prod` в `ui/Dockerfile`, `VITE_*` вшиваются при сборке через `ARG`. Локальный `yarn dev` направлять на задеплоенный бэкенд через `VITE_API_URL`.

## Правила для агента
- Первый запуск на новой машине: скилл `/setup` (проверка инструментов, `.env`, `docker compose up`, Railway). Деплой: `/deploy`.
- Перед первой фичей заполняется [docs/DOMAIN.md](docs/DOMAIN.md): проблема, сценарий, сущности, API, экраны, деление работы. Модели и эндпоинты делаются по нему, не наоборот.
- Изменил `schemas.py` или роутер на бэке: перегенерировать `yarn api:types` в `ui/` и закоммитить `api-types.ts` тем же коммитом. Красный `tsc` на фронте после этого чинится, а не откатывается.
- Перед правкой прочитать файл целиком. Не трогать файлы, не связанные с задачей.
- Не создавать новый файл, если можно дописать в существующий по правилам выше.
- Новая зависимость только через `uv add` / `yarn add` с обновлением lock-файла и раздела «Технологии» в README.
- После изменения запустить `uv run ruff check . && uv run ruff format --check .` в `app/` или `yarn lint` в `ui/` и показать вывод. Не говорить «готово», если он красный.
- Не переписывать работающее ради красоты. Минимальный диф, решающий задачу.
- README обновляется тем же коммитом, что и фича. README не обещает того, чего нет в коде.

## Стоп-лист
Не делать без явного требования задачи: авторизация и учётные записи, кеши, очереди, микросервисы, рефакторинг работающего кода, «на будущее». Тёмная тема и пагинация появляются по реальной потребности, не заранее.
